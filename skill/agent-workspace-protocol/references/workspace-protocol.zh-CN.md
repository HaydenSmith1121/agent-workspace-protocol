# 智能体工作区协议

本文件是工作区的规则正本。`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、
Cursor 规则和 Copilot 说明都只是指向本文件的适配入口，不能维护互相竞争的
完整副本。

## 0. 目的

新的人和智能体在修改任何内容之前，必须能回答四个问题：

1. 哪些内容是权威内容？
2. 哪些是输入，哪些只是输出或历史？
3. 应该先读什么，读到什么时候可以停止？
4. 新内容应该放在哪里，如何登记，如何标记状态？

目标不是让目录看起来整齐，而是让上下文可判断、可切片、可追溯。

## 1. 核心原则

### AWP-1：单一事实源

每个长期有效的事实、规则、规范或决策只保留一个正本。目录和摘要只链接正本，
不能复制出第二份完整规则。

### AWP-2：权威分层

| 层级 | 内容 |
| --- | --- |
| L0 | 用户当前指令 |
| L1 | 当前有效的工作区规则 |
| L2 | 当前有效且权威的规范、契约 |
| L3 | 代码和可执行测试 |
| L4 | 派生输出，例如报告、导出文件、生成文档 |
| L5 | 历史，包括会话记录、归档和草稿 |

高层级覆盖低层级。某个输出不会因为更新得更晚，就自动变成要求。

### AWP-3：先地图，后手册

自动加载的入口文件应当是简短的导航地图。详细流程放在参考资料中，只在相关时读取。

### AWP-4：状态、权威和来源

正式文件必须能够回答：

- 它是什么类型？
- 它是有效、草稿、已取代、已废弃还是已归档？
- 它是权威、派生还是非权威？
- 它来自哪里？
- 最后一次实质性更新是什么时候？
- 是否已经验证？

### AWP-5：输出不是输入

AI 生成的交付物和导出文件默认属于输出层，默认不具有权威性。只有经过用户明确
批准，或者经过可复现的验证和晋升流程，它们才可以成为输入。

### AWP-6：代码与知识分离

应用代码通常拥有独立的版本控制。知识工作区只保存代码仓库地图、用途、分支、
入口文档和经过验证的提交锚点。不要仅仅为了让代码可搜索，就把源码复制进知识层。

### AWP-7：当前状态、决策和历史分离

- 当前状态保持简短，并替换已经过时的结论。
- 决策记录解释为什么做出某个长期选择。
- 会话记录解释发生了什么，属于非权威历史。

不要让不断增长的会话日志成为当前事实的唯一存放位置。

### AWP-8：稳定的顶层分类

优先使用少量、稳定的顶层分类。只有说明现有分类为什么无法容纳新内容，并更新目录
说明后，才新增分类。

### AWP-9：敏感数据隔离

凭证不能复制到摘要、示例、报告、日志或生成物中。应使用密钥管理工具，或者使用
明确加入忽略规则的本地文件。如果凭证已经暴露，先轮换凭证。

### AWP-10：显式暴露冲突

如果两个权威来源冲突，而权威顺序无法解决冲突，应停止受影响的写入并询问用户，
不能静默猜测。

## 2. 默认工作区布局

这是默认布局。只有同时更新本协议和目录说明后，才能重命名或合并分类。

| 路径 | 用途 | 默认可信度 |
| --- | --- | --- |
| `MEMORY/` | 长期工作区记忆 | 高，按子类型判断 |
| `10-docs/` | 需求、设计、手册、会议记录 | 有效时为输入 |
| `20-projects/` | 项目知识、计划、状态、代码地图、本地工具 | 中 |
| `30-data/` | 原始数据、处理后数据和数据字典 | 中 |
| `40-deliverables/` | 最终报告、导出文件、演示文稿 | 派生输出 |
| `50-assets/` | 图片、字体、样式、静态模板 | 中 |
| `60-research/` | 外部研究和参考资料 | 中低 |
| `90-temp/` | 草稿和中间结果 | 最低 |
| `99-archive/` | 为追溯而保留的旧内容 | 历史 |

根目录文件应限制为导航和治理文件，例如 `README.md`、`AGENTS.md`、智能体适配器、
`.gitignore` 以及顶层分类目录。

## 3. 记忆结构

推荐的 `MEMORY/` 结构如下：

| 路径 | 用途 |
| --- | --- |
| `MEMORY/01-rules/` | 当前有效的用户规则和本协议 |
| `MEMORY/02-structure/` | 目录、命名和分类规则 |
| `MEMORY/03-sessions/` | 非权威任务历史 |
| `MEMORY/04-glossary/` | 术语和缩写 |
| `MEMORY/05-state/` | 简短的当前状态摘要 |
| `MEMORY/06-decisions/` | 架构和流程决策记录 |

`MEMORY/README.md` 是索引。每一个新的长期记忆条目都必须登记在那里。

## 4. 元数据标准

`MEMORY/`、`10-docs/`、`20-projects/`、`30-data/`、`40-deliverables/` 和
`60-research/` 下的正式文件应使用 YAML front matter。

建议字段：

```yaml
---
id: AWP-000
type: rule
status: active
authority: authoritative
scope: workspace
source: user
updated: 2026-01-01
verified: pending-user-review
derived_from: optional/path/or/url
supersedes: optional/path
sensitivity: internal
---
```

受控值：

| 字段 | 可用值 |
| --- | --- |
| `type` | `rule`, `spec`, `reference`, `output`, `session`, `decision`, `data`, `asset` |
| `status` | `draft`, `active`, `deprecated`, `superseded`, `archived` |
| `authority` | `authoritative`, `derived`, `non-authoritative` |
| `verified` | `verified`, `pending-user-review`, `not-verified` |
| `sensitivity` | `internal`, `sensitive`, `credential` |

如果工作区规则明确允许，适配器和简单 README 可以豁免，但内容仍必须简短准确。

## 5. 阅读协议

按以下顺序读取：

1. 最近的智能体入口地图。
2. 工作区记忆索引。
3. 仅与任务相关的有效规则。
4. 当前状态。
5. 相关分类的 README 或索引。
6. 具体文件。
7. 只有必须理解行为时才读取代码，并记录使用的代码版本。

不要批量读取无关目录。对于长文件，先读取元数据、标题和摘要。

## 6. 不会自动成为输入的内容

以下内容默认不是要求，也不是当前事实：

- `40-deliverables/` 下的最终输出；
- `90-temp/` 下的草稿；
- `99-archive/` 下的归档内容；
- 会话日志；
- 状态为 `draft`、`deprecated`、`superseded` 或 `archived` 的文件。

只有当用户明确引用它们，或者经过记录的晋升流程改变其状态和权威性后，它们才能
作为输入使用。

## 7. 写入协议

写入前：

1. 检查是否已经存在正本。
2. 判断分类、状态、权威性和来源。
3. 判断是否需要更新记忆索引。
4. 判断是否需要决策记录。
5. 检查凭证和敏感数据。

写入后：

1. 添加或更新元数据。
2. 更新相关索引。
3. 将长期有效的当前结论提炼进状态文件。
4. 工作区要求时，记录简短的会话条目。
5. 将替代内容标记为 `superseded`，并链接替代文件。
6. 清理临时内容，或明确标记必须保留的内容。

不得静默覆盖长期内容，也不得复制正本规则。

## 8. 新规则接收与自动归位

安装 skill 或初始化工作区本身不会在后台监听文件变化。只有当智能体进入工作区、
读取了入口地图和本协议，并在执行任务时新增或修改规则，它才会按以下规则分类。
如果没有智能体参与，手动创建的文件不会自动移动。

| 新增内容 | 默认存放位置 | 是否权威 | 需要更新 |
| --- | --- | --- | --- |
| 工作区长期规则 | `MEMORY/01-rules/<topic>.md` | 是 | `MEMORY/README.md` |
| 目录、命名、分类规则 | `MEMORY/02-structure/` | 是 | 目录说明和索引 |
| 当前事实、状态或结论 | `MEMORY/05-state/current.md` | 派生摘要 | 链接正本 |
| 重要决策及原因 | `MEMORY/06-decisions/NNNN-<topic>.md` | 是 | 决策索引 |
| 某次任务的过程记录 | `MEMORY/03-sessions/YYYY-MM-DD-<topic>.md` | 否 | 必要时登记 |
| 需求、设计、规范或契约 | `10-docs/` | 经确认后为是 | 相关索引 |
| 最终报告、导出物或演示文稿 | `40-deliverables/` | 否，派生 | 来源和状态 |
| 暂时无法分类的素材 | `90-temp/inbox/` | 否 | 任务结束前分类或删除 |

执行规则：

1. 先搜索是否已有正本；如果存在，修订正本，不创建平行副本。
2. 在写入前说明分类结果和位置。
3. 长期规则写入 `MEMORY/01-rules/`，并更新 `MEMORY/README.md`。
4. 如果规则改变当前结论，同时更新 `MEMORY/05-state/current.md`。
5. 如果规则改变结构、权限边界或权威模型，新增决策记录。
6. 任务结束时，把 `90-temp/inbox/` 中仍有价值的内容移到长期分类。

## 9. 输出晋升

将生成输出晋升为输入时：

1. 明确消费者和晋升范围。
2. 验证内容，或取得用户明确确认。
3. 将状态改为 `active`，将权威性改为 `authoritative`。
4. 移动到正确的正本分类。
5. 在状态文件或决策记录中登记晋升。

晋升是有意识的正式事件，不是普通的文件移动。

## 10. 代码地图

每个外部代码仓库应在工作区代码地图中有一行记录：

| 字段 | 含义 |
| --- | --- |
| Repository | 稳定的短名称 |
| Location | 仓库 URL 或外部路径 |
| Purpose | 该仓库负责什么 |
| Default branch | 作为基线使用的分支 |
| Entry document | 通常是仓库的 `AGENTS.md` 或 README |
| Verified commit | 最近一次验证结论使用的提交 SHA |
| Verified date | 验证锚点的时间 |

每个代码仓库应携带自己的智能体说明、构建和测试命令以及文档。知识工作区链接到
它，而不是复制它。

## 11. 密钥和敏感数据

1. 凭证优先使用真正的密钥管理工具。
2. 如果必须使用本地密钥文件，应放在版本控制之外，并在首次提交前忽略其路径。
3. 不得把密钥复制到会话摘要、报告、提示模板、示例或适配器中。
4. 只记录密钥引用的位置和用途，不记录值。
5. 如果凭证被提交或暴露，应立即轮换。

## 12. 命名和链接

1. 目录使用小写短名称和两位排序前缀。
2. 文件名不得包含空格或平台保留字符。
3. 按日期排序的文件使用 `YYYY-MM-DD-` 前缀。
4. 文本使用 Markdown 和 UTF-8。
5. 工作区内使用相对链接。
6. 每个工件只保留一个正本路径；路径移动时更新索引。

## 13. 任务生命周期

### 开始

- 读取入口地图和相关索引；
- 判断输入的权威性；
- 记录代码版本和环境假设；
- 写入范围不明显时，先说明计划写入范围。

### 执行

- 渐进读取；
- 不隐式晋升派生内容；
- 暴露未解决冲突；
- 临时工件保留在临时分类。

### 结束

- 将长期文件放入正确分类；
- 添加状态和来源；
- 更新索引和当前状态；
- 明确保留或清理临时文件；
- 报告路径、验证证据和未验证事项。

## 14. 文档维护

定期检查：

- 根目录没有意外文件；
- 索引覆盖长期条目；
- 链接在区分大小写的系统上可以解析；
- 输出被标记为派生；
- 当前状态与正本规则不矛盾；
- 代码锚点仍然存在；
- 被取代的文件指向替代文件；
- 临时目录已清理；
- 预期密钥位置之外没有凭证。

## 15. 修改协议

实质性修改应：

1. 说明失败或需求。
2. 至少考虑一个替代方案。
3. 记录决策。
4. 更新本协议。
5. 更新索引和适配器。
6. 标记被取代的内容。
7. 验证结果。

如果工作区没有决策记录流程，应在进行大型结构调整前创建。

## 16. 最低合规检查

- [ ] 每个长期事实只有一个正本。
- [ ] 权威层级明确。
- [ ] 输出和输入可区分。
- [ ] 代码和知识边界有记录。
- [ ] 当前状态、决策和会话分离。
- [ ] 所有智能体适配器都指向本协议。
- [ ] 跟踪文件中没有密钥。
- [ ] 索引和链接是最新的。

## 17. 定制

工作区可以修改目录名称、编号、元数据字段和适配器选择。如果没有记录等价机制，
则不能移除本文件开头四个问题的答案要求。

定制时：

1. 同时更新本协议和结构说明。
2. 更新每个适配器和索引。
3. 保持权威模型明确。
4. 使用新的智能体或全新上下文复核工作区。
